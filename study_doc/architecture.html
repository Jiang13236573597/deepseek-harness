00 · 全景

一句话看懂 dsh

模型适配器、工具注册表、会话日志、权限策略，甚至 agent loop 本身，都是 Cordis 插件。

  • 全是插件：没有可以改动的特权内核，扩展就是在旁边再挂一个插件。
  • 组合即数据：profile 把多个 bundle 的 YAML 补丁层叠成一棵插件树。
  • 应用接管：Web 服务器、headless 执行器、SDK 与 ACP 服务器都是树里的普通插件。
  • 日志为本：每个 Agent 的对话写进 append-only 的 Session 事件日志。

02 · 插件加载

Cordis 的五个核心概念

插件

导出 apply(ctx, config) 的模块，可附带 name、inject、Config；或者一个 Service 子类。

Context

服务仓库：服务占用 ctx.tools、ctx.llm 这样的 key，使用方按 key 取，不 import 实现。

inject

声明依赖的服务；服务全部就绪前插件不运行。加载顺序由依赖表达，不靠手工排序。

类型化事件

通过 declaration merging 声明事件，按 emit、waterfall、parallel、serial、bail 五种模式派发。

effect

注册即可撤销：ctx.effect() 与 ctx.on() 返回 disposer，插件卸载时自动撤销。

读法：Context 是“谁提供什么”，inject 是“我需要什么”，事件是“我们怎么协作”，effect 是“我走后不留痕迹”。
参考：docs/cordis-primer.md
02 · 插件加载

一个真实的最小插件：timeout-policy

import type { Context } from '@deepseek-ai/cordis'

export const name = 'timeout-policy'            // ①
export const inject = ['tools']                 // ②

export function apply(ctx: Context): void {
  ctx.on('tools/execute', async (exec, next) => { // ③
    const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs
    if (timeoutMs === undefined) return next()    // ④
    // 给 exec.signal 加上超时，再调用 next()
    // 若本插件的计时器触发，把结果改写为 TOOL_TIMEOUT
  })
}

Fiber：插件实例的六种状态

  • 每次 ctx.plugin(plugin, config) 创建一个 Fiber
  • Fiber 管理依赖、原始配置与生效配置、effect 清理
  • 状态变化发出 internal/status；进出 ACTIVE 时通知依赖它所提供服务的插件

02 · 插件加载

依赖 epoch：为什么配置行的顺序无关

_refresh()：epoch = 自身修订号 + 每个 inject 服务当前实现的 uid；任一依赖缺失则为 INACTIVE。
  • 从 INACTIVE 变为可用 → 加载；其他变化 → 先卸载，epoch 仍可用就按新依赖重新加载
  • 卸载有顺序保证：服务提供者要等所有依赖者卸载完毕，才撤销自己的 effect
  • 结果：YAML 行顺序没有加载语义，替换任何服务实现都会自动级联重载
源码：vendor/cordis/src/fiber.ts（_refresh、_setEpoch、_unload、_reload）

02 · 插件加载

插件包从哪里来

① bundle 的位置

resolveBundleDir() 先查 dsh 安装目录，再查 profile 目录。

所以 dsh-base 等内置 bundle 总是来自当前运行的这份安装，不会被 profile 里的旧副本顶替。

② 模块解析

PluginPackages 在内存中拦截 Node 的 ESM 与 CommonJS 解析器，并让 Worker 线程看到同一张包表。

包表在任何插件被 import 前算好且不可变；profile 重新组合时发布完整的后继版本。不写符号链接。

③ 兼容性检查

evaluatePluginCompatibility() 读取 engines.dsh（没有时读 dsh 的 peer 依赖），不 import 插件代码。

不兼容的 bundle 被跳过；可以用 dsh plugin allow-version <pkg@ver> --dsh-version <exact> --accept-risk 为精确版本登记豁免。
源码：app-boot/src/profile.ts · profile-resolution/service.ts · plugin-compatibility.ts

03 · 权限控制

两个旋钮，加上工具管线里的检查点

默认不逐次审批。命令和文件写入先在沙箱里执行；只有模型主动申请越过沙箱（sandbox_permissions）时，才请人或自动化流程做一次性批准。
  • 沙箱模式 sandbox/mode：命令和文件工具能产生什么文件副作用
  • 审批策略 approval/policy：需要批准的操作是去问，还是直接拒绝
  • 权限预设：把两个旋钮打包成一个可选的“权限模式”
  • 两个旋钮都以 Session 事件保存，重启和回放后依然有效
参考：sandbox.md · approval.md · permission-presets.md

SurfaceOp

'append' 追加到末尾；{ op: 'replace', startSeq, endSeq } 用本事件替换一段现有节点，两端都包含。

04 · 对话管理

持久化与崩溃恢复

  • create 时不写任何内容，首次 append 才落盘；每批写入都 fsync
  • 默认用带校验和的 Zstandard 帧；已提交的事件从不改写
  • checkpoint 落盘失败时，模型调用和工具都不会执行
  • 崩溃后：最后一个 turn 原样保留，恢复时补写 interrupted；残缺的末行或末帧被丢弃
  • 没有结果的工具调用得到“结果未知”，不自动重试有副作用的操作

  • Fork：在 turn 边界分叉，子 Session 先保存父 Session 的前缀，再追加自己的事件；分叉点仍打开的 turn 以 forked 关闭

处处 fail-closed：不确定就拒绝

位置失败时的行为
审批没有应答者、应答者抛错或返回不合规的值 → unavailable，按拒绝处理
沙箱没有可用后端 → SANDBOX_UNAVAILABLE，绝不无沙箱执行
Checkpoint落盘失败 → 不调用模型、不执行工具
启动必需的行未激活 → StartupError，诊断列出缺少的服务

05 · 设计巧思

持久化格式只增不改

相邻迁移包

每个包只负责一步：session-format-v0-to-v1 … session-format-v3-to-v4。写入版本由 SESSION_FORMAT_VERSION 决定（阅读时为 4）。

open() 选择版本最高的规范代文件：当前版本走普通快速路径；历史版本解码、迁移到当前格式并校验。

写开时发布后继文件

以写方式打开旧会话时，在原文件旁发布当前版本命名的文件；已提交的旧文件从不重命名、覆盖或删除。

同目录临时文件→Worker Thread 校验→复查源文件 revision→不覆盖地发布

例：session.v2.jsonl.zstd 字节不变，旁边新增 session.v4.jsonl.zstd。准备之后源文件若有变化，这次写开被拒绝。

读开只在内存迁移

读开在内存里解码、迁移并校验一次，不发布后继文件。stat 和 list 只读最高代的文件头，不读事件行，也不启动迁移。

保留旧文件不代表支持降级或回退读取，只保证已提交的数据不因升级而丢失。

参考：session-persistence-jsonl · SESSION_FORMAT_VERSION · 格式迁移决策记录
